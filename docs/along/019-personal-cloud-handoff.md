# Personal workspace cold handoff v1

This change preserves one existing personal workspace when its original phone connects to an existing cloud Along deployment. It does not create goals again, upload credentials, or enable remote push. The operator first verifies the cloud destination and waits for in-flight work to finish. Production execution belongs to the release owner.

## Scope and invariants

- The first release supports a dedicated business database containing exactly the selected user and exactly the explicitly selected goal IDs. An unexpected user/goal, unsupported table or schema, active work/delivery/review, or a different nonempty destination is refused. This is an intentionally bounded cold handoff, not a merge engine.
- Original user/device/goal/task/message/event IDs, revisions, conversation/background audience, result evidence, executions, trigger occurrences, reminder cadence, grants/revocations, and sync sequences survive unchanged.
- Only the schema-18 Along business database is exported. No DSH state directory, profile, Host files, bridge/pair/model/API keys, Keychain, or Hy-Memory backend directory enters the package. External memory backend locators are cleared from copied business memory rows so a cloud index cannot address another backend's private records. Existing governed facts with no index IDs are served as explicitly degraded SQLite recall under the same ownership, applicability and withdrawal checks; this does not re-extract old chat or upload a backend directory.
- Source and target must be cold, protected by the same directory lock as Runtime. Source freeze and staged target fences block startup before the store opens. The release owner must also disable an older immutable launcher that predates this guard. No HTTP import endpoint is added.
- Every exported table/column is checked against the current schema. Rows are transactionally read; import is one transaction with foreign-key checking. A package is never a SQL script, cannot name arbitrary tables/columns, and cannot overwrite target rows.
- Stage imports only to an empty dedicated business database. Repeating an identical staged package is idempotent; a migration ID bound to another digest is refused. Activation is a distinct operator step after target validation and permanent source retirement. Source abort is permitted only before source retirement releases the activation permit; post-cutover rollback requires migration of the new cloud delta.

## Frozen manifest contract

`format` is `along-personal-handoff/v1`. Fields are `migrationId`, `sourceUserId`, `sourceDeviceId`, `schemaVersion` (18), `targetOrigin`, `createdAt`, `goalIds`, `snapshotSHA256`, `syncPrefixSHA256`, `syncHighWaterMark`, `activationPermitSHA256`, `hostCompanionSHA256`, `sourceHolds`, and `tables` (`{name,rowCount,sha256}` in lexical table order). The package additionally has `data` keyed by exactly the allowed table names. The manifest is a checksum/continuity record, not an authorization signature: Along Host must authenticate its source and sign the narrow Native handoff proof separately.

`hostCompanionSHA256` is mandatory lower-case 64-hex SHA256 of the separately authorized Host companion's canonical JSON, using this document's canonicalization. Administrative `inspect` and `freeze-source` require `--host-companion-sha256 DIGEST`; P1 binds this digest unchanged in its manifest, persisted checkpoint and Source proof, but does not read or interpret Host files. P2 validates the sidecar and exact digest before target activation; the complete signed manifest hash binds its original settled notification ledger and source journal. The sidecar contains no newly generated hold events, avoiding a digest cycle: P2 derives the same target unavailable events from manifest `sourceHolds` using the recipe below. No whole Host directory, raw history, gateway data, bearer or keys are added to the SQLite package.

`sourceHolds` is derived from the frozen data, never supplied by the model: each ready OKX source advertising trading_history gets `{provider:"okx",goalId,reason:"cloud_history_unsupported",sourceEventId,sourceGeneration,sourceRevision}`. The cloud's history guard remains intact. The original source event/read and product report records remain historical evidence; staging appends a deterministic, authorized `unavailable` source event at the same generation and next revision with no capabilities, using SourceStateStore's existing acceptance primitive. Its reference is explicitly a cloud-compatibility hold, not a new device read. No read/metric is fabricated and no old source event is rewritten. A `goal_updated` sync fact is appended after the complete preserved original prefix.

The target fence/status additionally carries `targetReceipt:{snapshotSHA256,syncHighWaterMark,sourceHolds}` for the post-hold staged state. Receipt sourceHolds add `eventId`, resulting `generation/revision`, and `state:"unavailable"`. Source fences do not carry this target-only field. Stage replays validate either the pristine import or the exact deterministic post-hold state and complete the same hold idempotently. Activation checks the actual database against this receipt and the deterministic expected package transformation before any Worker starts. Host/Native must require the manifested holds in the authenticated active receipt, and must not advertise these sources as connected. This supplements the original imported snapshot; it does not redefine its hash or old sync prefix.

Canonical JSON recursively sorts object keys by Unicode code-unit order; arrays keep their explicitly defined order. No whitespace is emitted. Values are JSON null, finite safe numbers, strings, arrays and objects; SQL BLOB and unsafe integers are refused. SHA-256 is lowercase hex over UTF-8 canonical JSON. Table rows are sorted by canonical JSON, except source_state_read preserves ascending source rowid order because the existing latest-read lookup uses rowid as a causal tie-breaker. `snapshotSHA256` hashes the complete portable `data` object; `syncPrefixSHA256` hashes original `sync_outbox` rows in numeric seq order, excluding only mutable delivered_at receipt timestamps. The manifest itself is bound by the separate Host proof.

### Actual Source continuity proof

The exact imported database stores reserved meta key `personal_handoff_checkpoint` inside the import transaction. Its value is `{version:1,phase:'target_staged',manifest}`; the same transaction that applies source holds adds targetReceipt. Activation verifies the migration-only permit and actual staged data, marks this checkpoint target_active through AlongStore, then persists the startup fence target_active. A crash between these commits leaves the file fence staged and Runtime cannot start. Retry finishes the same activation. This deployment authority marker is a recognized meta key but deliberately excluded from portable personal `data.meta`/snapshot hashes (avoids a circular receipt hash and copying a prior deployment authority). All ordinary meta keys remain strict; an invalid checkpoint fails closed.

**Internal read-only route:** `GET /along-source/api/workspace-handoff/status`. It uses the existing bridge token and server-bound user/device headers; no identity from a body and no import/mutation route is added. The optional user_id query, if present, must match the bound header identity. The actual opened AlongStore checks its own DB checkpoint, current user/device, and its own directory's matching target_active fence/receipt. Only an accepting Runtime returns HTTP200. No matching active import is 404; not-ready Runtime is503; existing bridge auth remains401/403. It additionally recomputes the preserved original sync prefix from this database: numeric seq order, every semantic row field, excluding only mutable delivered_at ACK timestamps. Later legitimate cloud rows are outside the original high-water mark.

HTTP200 body is `{format:'along-personal-handoff/source-status/v1',phase:'target_active',migrationId,userId,deviceId,manifestSHA256,snapshotSHA256,syncPrefixSHA256,syncHighWaterMark,activationPermitSHA256,hostCompanionSHA256,sourceHolds,targetReceipt}`. These are the original manifest snapshot/prefix and complete-manifest hash plus the post-hold receipt. Host must query this route through its actual bridge and compare every field with its signed handoff claims. A separately configured Host state file, ready=true, or registering the same user/device into an empty Source is insufficient. Wrong/empty/old Source fails closed even when ordinary connection/status could succeed. The endpoint does not echo business rows, health values or any secret.

Handoff status includes the same manifest identity fields plus `phase`: `source_frozen`, `source_retired`, `source_aborted`, `target_staged`, `target_active`, or `target_aborted`. Staging and activation must be offline; the cloud Host/phone must verify the same migration ID and digests. A persisted fence blocks normal Runtime startup except `source_aborted` and `target_active`. Public status contains no credential or health value.

To make pre-activation abort safe, freeze creates a random 256-bit activation permit and publishes only its SHA256 commitment in the manifest. The permit remains in the private source fence, never in the export. `retire-source` irreversibly fences the source before writing the permit to a separate owner-only transfer file. Cloud activation requires that exact permit. `abort-source` works only while frozen, before the permit has been released. A retired source cannot restart or be aborted by this tool; post-cutover rollback must retain the cloud delta. A staged target may be aborted but cannot later activate. Thus a lost activation acknowledgement cannot cause this tool to restart the old writer.

## Release sequence and validation

1. Inspect the exact source/destination and run a synthetic rehearsal; do not infer cloud identity from public health.
2. Preserve the original phone and local full recovery backup separately. Wait for current work and pending ordinary deliveries/reviews to settle; stop and persistently disable the source launcher.
3. Export the whitelist business package and persist source_frozen under the directory lock. Transfer over an authenticated encrypted transport.
4. Import into an empty isolated target with target_staged fence; compare all table counts/digests and sync prefix. No workers, schedules, or notifications run during staging.
5. Persistently retire source before releasing the activation permit, then activate the sole cloud writer. Along Host can now serve an authenticated handoff receipt without depending on a staged/stopped Source. A lost activation ACK is recovered from the same migration status; new legitimate cloud writes must not be compared back to the old frozen snapshot.
6. Along Host issues a new cloud device credential retaining original business user/device IDs and an independently authenticated one-time Native proof. The proof binds the entire manifest digest (including activationPermitSHA256) and source retirement; Host signs exact UTF8 payload bytes and Native verifies those original bytes rather than reserializing Foundation JSON. The old Mac bearer never travels to cloud. Native retains pending event IDs/payload, drafts, direct chat, notification namespace and original system requests.
7. Native verifies the active cloud receipt and commits the connection. If this fails, the cloud remains sole authority and the phone retains its queue for the same migration; never automatically restart source. Read back natural phone upload ACK, healthy review/keep/change, task details, and system reminder state. APNs and actual notification delivery remain separate acceptance layers.

## Administrative commands

Build with the supported Node runtime, then run `node scripts/along-handoff.mjs`. `--data-dir` names the dedicated Along directory and `--state-dir` names its separate DSH directory. Every operation except read-only status requires both cold directory locks and checks actual orchestrator ticket assignments, undelivered inputs, evaluating threads, pending replies and persisted effects. Export also rejects unfinished work links/run records, ordinary delivery pending/failed, unsettled health dispatches, pending memory maintenance/SDK operations, source reads, research requests and pending/dispatched task occurrences. No operator-provided idle boolean can bypass these checks.

```sh
node scripts/along-handoff.mjs inspect --data-dir SOURCE_DATA --state-dir SOURCE_DSH --user SOURCE_USER --device SOURCE_DEVICE --goals GOAL_ID_1,GOAL_ID_2 --target-origin https://along.example.com --migration-id MIGRATION_ID --host-companion-sha256 HOST_COMPANION_SHA256
node scripts/along-handoff.mjs freeze-source --data-dir SOURCE_DATA --state-dir SOURCE_DSH --user SOURCE_USER --device SOURCE_DEVICE --goals GOAL_ID_1,GOAL_ID_2 --target-origin https://along.example.com --migration-id MIGRATION_ID --host-companion-sha256 HOST_COMPANION_SHA256 --package PRIVATE_PACKAGE_FILE
node scripts/along-handoff.mjs stage-target --data-dir EMPTY_TARGET_DATA --state-dir TARGET_DSH --package PRIVATE_PACKAGE_FILE
node scripts/along-handoff.mjs retire-source --data-dir SOURCE_DATA --state-dir SOURCE_DSH --migration-id MIGRATION_ID --permit-file PRIVATE_PERMIT_FILE
node scripts/along-handoff.mjs activate-target --data-dir EMPTY_TARGET_DATA --state-dir TARGET_DSH --migration-id MIGRATION_ID --package PRIVATE_PACKAGE_FILE --permit-file PRIVATE_PERMIT_FILE
node scripts/along-handoff.mjs status --data-dir TARGET_DATA
```

The CLI prints counts/digests or handoff status, never business rows or permits. Package, permit and fence files are 0600. The permit is a new migration-only secret, not a copied pairing/model credential. Unknown/nonempty target data is refused before writing a target fence. Interrupted stage may retain a staged empty target and can safely retry; committed import and same-package stage retry preserve identical rows. `abort --data-dir ... --state-dir ... --migration-id ...` resumes a frozen source only before permit release, or leaves a staged target permanently disabled. Retired source and active target cannot be aborted with this tool.

The SQLite package is not the entire deployment state: Host source journals/grants/daily authorizations/notification route ledgers and iPhone producer scopes require a separate scoped inventory and handoff by the client/release owner. Existing ready source facts alone do not prove the cloud Host can serve their references. Never copy the whole Host directory or represent this package as full-system migration.

`tests/fixtures/personal-handoff-manifest.json` is a generated, synthetic header for the cross-repository Host/Native proof contract. `tests/fixtures/personal-handoff-history-receipt.json` adds a real synthetic ready-history source and its deterministic unavailable hold receipt. Both contain no personal data or live credentials.

Tests cover exact preservation, schema/table/column refusal, cross-user/goal isolation, corruption, cold/drain requirements, repeat import, target conflicts, stage/startup fencing, failed activation, and atomic rollback. Full `pnpm check` is required before PR; no production data or device is used by these tests.

## Retired review dispatch continuity (2026-11-25)

Goal: a cold handoff must preserve a NULL-result dispatch that Runtime has explicitly retired, together with its due, repair or source-review history. NULL alone does not prove that work is pending. A genuinely pending dispatch still refuses inspect/export, package validation, staging and activation.

Scope: align the business-drained check with the schema-18 `HealthStore.pending` retirement rule. One valid `retired=1` association in the due, repair or source-review tables suffices, even when a dispatch has multiple associations. The association must match dispatch/task ownership and references and use nonempty string event identities; SQLite permits NULL in a single-column `TEXT PRIMARY KEY`, but SQL `=` does not join NULL identities. A missing, active or invalid association does not itself qualify. No result is fabricated, no review row is deleted or rewritten, and the other handoff guards remain in force.

Regression coverage: [`tests/along-retired-dispatch-handoff.spec.ts`](../../tests/along-retired-dispatch-handoff.spec.ts) uses temporary databases and synthetic identities to exercise the pending query, all three review kinds, valid and invalid associations, and cold handoff through Runtime reopen. It checks that original dispatch/review rows and their digests survive without replacement work or notifications. This is not a production handoff or an Along client pin update.
