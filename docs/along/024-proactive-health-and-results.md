# Proactive goal review and readable task results

## Goal and boundaries

An active health-related goal needs a durable opportunity to reconsider today's actions and tonight's sleep preparation when the user's local day changes or relevant observations change. It must not depend on opening the App to run the scheduler. A review is not an obligation to edit tasks or notify; the Worker decides relevance and the minimum change from original intent, current sleep/workout facts, memory, constraints and existing commitments. Missing, fragmented or stale data remains explicitly unknown. No new goal or medical diagnosis is inferred.

The original task graph and receipt/revision protections remain authoritative. Same-goal automatic work queues, newer user input wins, `keep` preserves all task fields, fixed user deadlines are not reinterpreted as Agent preferences, and background work never goes into chat.

## Design

1. Reuse the current HealthFollowup worker pipeline and a persisted per-goal daily-review marker, keyed by user/goal/input version/local date/timezone (additive schema18). Select the user's timezone only from trusted accepted data, never the host timezone. Repeated passes and restarts reuse the same dispatch. Genuine new observations still get their normal health dispatch. Relevant reviews persist next_review_at: the Worker can choose a future next-local-day instant within 48 hours; the fallback uses the observed wake clock plus 30 minutes, or 09:00 local if unknown. This clock is a review opportunity, not a prediction or notification. Missed days coalesce to today's review. Empty watched types do not start a schedule on unrelated keep; an actual applied goal plan may explicitly request a planning-only next review without inventing a health metric. This same-input clock survives unrelated observations and missing/stale health data; the daily read excludes expired facts, retains the trusted schedule timezone and says there are no current observations. New accepted source timezone invalidates/rebases the old clock. New user input, inactive goal, authorization/auto state and stale observations remain checked.
2. Expose why the review occurred and a bounded context describing the local day, prior reviewed facts and current observations. A daily review may use the existing still-applicable facts, but must not pretend a new HealthKit observation arrived. Skip unrelated goals through the existing watched-type relevance chosen by the Worker.
3. Strengthen the existing task/domain skill: reason about last-night duration and observed bounds separately, recent activity and availability; choose useful actions across recovery, varied movement, sleep preparation and nutrition only where supported by the real goal and profile. Persist executable triggers and reminders through the same ChangeSet interface. Fetch outside evidence for local/time-sensitive recommendations; generic advice does not need invented citations or research tasks.
4. Add result_presentation v1 to actual background task sync results (the finish input is presentation). Preserve the existing presentation='execution' marker. Strict bounded display objects provide a short title/summary, a few actions and optional full sections. Tool-derived calculations/history/recommendations use canonical verified facts rather than trusting alternate model numbers or risk claims. Complete verified result_text is <=16000 UTF16 units, while message.text/payload.text remains an explicitly labelled <=1200 preview so old Web88 clients still parse. Questions/reminder notes and ordinary chat do not gain a long-body permission. New display/result inputs reject lone surrogates; scalar-safe prefixes/chunks keep native Foundation JSON valid and section concatenation lossless. If display labels would exceed the presentation budget, the complete result_text remains authoritative rather than emitting partial “full” sections.
5. New HealthKit optional context fields mirror the native contract: up to seven recentSessions with observed activity/duration/associated statistics and indoor/outdoor/unknown, plus bounded sleep segment/stage summaries. Only aggregate summaries are admitted, not raw samples, UUIDs, coordinates, routes or private metadata. Corrected relevant observations invalidate the read snapshot at both ChangeSet commit and followup finish, so an old Worker cannot publish its plan as current; sub-threshold scalar noise and metric_version-only refreshes keep existing behavior.

6. Per-type health reads accumulate actual observations. Reading an absent steps/workout type does not erase a previously read sleep row. Unread dispatch facts remain a comparison baseline only; they are not silently claimed as read. This preserves the stale-observation guard while allowing selective reads and unknown metrics. Exact shipped main-v17 health trigger guidance remains bound across the package upgrade; arbitrary text/scope changes are still refused.

7. Clock source and recurrence_source have separate diagnostics. Daily means seven days and weekly means one weekday; explicit weekday-only subsets cannot become daily even under inferred cadence. For currently unsupported workday series the Worker can persist today's useful once actions and an honest next-day planning review, without claiming the entire native recurrence was installed or endlessly retrying invalid quotes.

## Research configuration

Along research continues to require authorized DeepSeek Search/Fetch, disabled original-question forwarding, public HTTPS/DNS and scoped evidence. A deployment using generic Auto/local-http does not automatically satisfy this contract. The current rc.5 public seam has no per-call provider override; Along therefore preserves the guard and exposes along_execution_capabilities as a local configuration check, not a network/authentication probe. Deployment must explicitly select deepseek-search-api / deepseek-fetch-api and sendOriginalQuestion=false using server-held credentials. A profile source change is not proof persisted cloud settings changed. No private runtime settings were modified in this development task.

## Acceptance

- The same local day/goal/input does not repeatedly dispatch when unchanged; next local day can dispatch even with unchanged relevant observations, and a restart preserves deduplication.
- New observation and input corrections are versioned, busy goal work serializes, finance/unrelated watched types are not daily spammed, old/missing data cannot become new facts, and timezone changes cannot revive stale work.
- Scenario evaluation covers late-but-sufficient sleep, short sleep, normal sleep, fragmented/unknown sleep, existing fixed commitments, workout variety and goal-relevant nutrition. Fixture execution is not a live LLM outcome.
- Result schema rejects excess fields, oversized strings and unbound display objects; complete text and presentation survive finish plus sync replay, while typed calculations/research still require actual receipts/sources and chat remains clean.
- Run typecheck, relevant runtime tests and full check/build before commit. No formal paired phone or cloud user data is used for test work.

## Actual model and native/client checks

The opt-in `tests/along-health-model-live.spec.ts` uses actual MiniMax-M3.1-Flash inference and current registered Along tools/SQLite with synthetic identities, while DSH transport is the test fixture. Enable only deliberately with ALONG_LIVE_HEALTH_EVAL=1 and an existing owner-only ALONG_LIVE_HEALTH_ENV_FILE; credentials never become model input or output. ALONG_LIVE_HEALTH_CASES selects affected cases, and ALONG_LIVE_HEALTH_OUTPUT writes a private local evidence file. Default check skips this network test. Four unmodified synthetic scenarios are in tests/fixtures/proactive-health-quality.json; their rubrics are for review, not fed to the model.

The initial real probe revealed goal drift/stock timing and a selective-read lifecycle defect; failures were retained, then prompt goal-fit/time semantics, read accumulation and actionable recurrence recovery were corrected. Subsequent late-sufficient/movement cases and the affected meal case achieved durable planning with fixed booking clocks and clean chat. Meal completed in the original nine-request budget (seven requests), with types:[], two current-day actions and a persisted next review. Evidence is across prompt iterations, not a claim that every positive result ran under one final hash or that production DSH/phone behavior was verified.

An actual current-Agent 6317-character isolated result was replayed through the unmodified old Web88 workspace parser and offline cache: a counterfactual raw-long-message wire was rejected, while preview(1200)+result_text was accepted and cached. The unchanged Unicode boundary probe now emits well-formed preview/summary/chunks; actual Swift Foundation JSONSerialization accepts the wire. These are protocol/native parser checks, not phone installation, notification delivery, public search success or cloud deployment.
