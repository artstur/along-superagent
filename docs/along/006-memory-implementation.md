# 长期记忆模块实施与验收

> 2026-11-16，阶段 D 独立模块及 Runtime 接线。规格以 [记忆与技能](002-memory-and-skills.md) §2 和 D6、D7、D13、D16、D18 为准。实现状态与实测结果在本文末尾登记，不把方案当作已通过。

## 1. 目标与范围

提供可独立运行和验证的 Memory Service：批量提取、SQLite 治理、Hy-Memory 常驻适配、有效记忆查询、即时撤回、上下文过滤及故障恢复。复用阶段 A 的用户、消息、目标与数据库事务；不直接改目标/任务状态、手机页面或配对协议。Runtime 接线见 §5；自动定时运行仍由阶段 E 调用批处理接口。

## 2. 实现方案

- `AlongStore.memory` 拥有记忆存储组件，共用同一个 SQLite 句柄与 `atomic`，仍是一个业务库、一个写入所有者。schema 升到 2，仅添加治理与操作表，保留 schema 1 的历史、任务和占位记忆表。
- `MemoryService` 只接收宿主绑定的 `userId/goalId`。提取输入从数据库重读，只接受用户入站聊天；助手消息、任务反馈和健康事件不作为长期偏好证据。一次批次按用户与范围分组，逻辑操作与每次 SDK 尝试分别落库；失败保留 pending，重启重试。
- Hy-Memory 2.0.16 由一个 Python 子进程持有，stdin/stdout JSON Lines（不监听网络端口）。SDK 使用 `pro/chat`、固定 Along Agent 身份、Chroma、关闭 graph/intention。密钥只由 Python 从 Mac 外部的 0600 env 文件读取，协议错误不回显 SDK 异常/提示词/密钥。TypeScript 有限时、单飞和进程退出恢复；超时结束整个子进程，避免晚到写入与后续请求重叠。
- Hy-Memory 结果必须再次分类并绑定原文引用：主体、明确/推断、长期/临时/目标约束、肯定/否定/引用/假设、范围、来源消息、冲突与更正关系。SQLite 验证原文引用确实存在、用户归属和适用范围，明确的长期肯定表达才可 active；推断只 candidate，冲突双方均不冒充当前有效事实，但保留带状态的历史上下文供模型理解。不用相似度作为生效或更正依据。合并后的新内容重新治理，不继承 SDK 节点的旧状态。
- 召回只把 SDK 节点 ID 用作排序提示，不直接返回 SDK 正文、画像、摘要或索引。输出正文来自 SQLite 治理记录，`memories` 仅含当前有效版本，`history` 保留同范围的非当前记录及状态/来源顺序，每次读取再查状态/到期/范围/来源撤回；SDK 不可用时降级读取 SQLite。调用结束时再次过滤，防止查询途中撤回仍返回旧结果。
- 撤回同步落治理修订、来源屏蔽及主题/范围截止序号，派生记忆沿来源关系一并撤回，登记后台清理。历史聊天不删，任务不改。**当前上下文行为（D18）**：保留未被直接撤回的数据库对话，不接受无来源的外部摘要。有效记忆与带状态的旧版本/候选/冲突/停用记录分开返回，让模型理解前后变化；当前明确要求优先。没有所有历史摘要的完整来源图，不宣称能精确脱敏或清除模型已读内容，也不按一次撤回截断整段历史。批量提取排除已撤回证据，重试与重启均不得复活。同一主题的新明确表达必须来自撤回之后的新消息，才可形成新记忆。
- 批量清理按用户重建 SDK 投影：撤回后的用户 SDK 数据整体删除，再重新提取未屏蔽的用户消息。清理未完成前 SDK 内容从不直接进入规划。这样覆盖 SDK 的派生摘要/画像/索引，不依赖单条 delete 的隐含级联行为；其他用户不受影响。SDK request id 仅记录在 attempt 内，不承担业务幂等。

重建也遵守保守窗口：撤回截止序号之前的消息，只允许用**仍有效记忆的原文引用**重建 SDK 投影，不重新发送整段旧聊天，也不再对当时尚未治理的历史做提取。否则某个旧消息没有被首次提取为证据、却表达相同偏好时，仍可能把已忘记内容重新写入 SDK。该限制只约束 SDK 投影重建，不再用于截断规划对话；历史展示数据始终保留。

固定版本核对：2.0.16 的 L0 画像是 user-scoped（不属于 `agent_id=along`），清理不能带 agent 过滤；`delete_all` 内部可能吞掉 VDB 删除异常并仍返回 success，因此删除后用全部 layer/status 查询验证确实无节点，失败继续保留清理项。Python 同时持有数据目录的排他文件锁，防止两个服务实例同时写 Chroma。

### P1 修复：重建期间保留 SQLite 降级

目标：撤回某条记忆后，其他有效记忆在 SDK 删除成功、重新提取失败时仍可查询，且返回 `degraded: true`。只修改 Memory Store、Service 及回归测试；跨范围屏蔽和过期冲突两项 P2 留待单独处理。

实现：在现有 SQLite `meta` 中持久化按用户区分的投影重建标记，与删除清理项、重置提取进度处于同一事务。待删除和待重建任一状态存在时均降级；删除已经成功的重试不再次清空 SDK。只有所有待处理操作与可提取消息都完成后才清除重建标记，失败、跨批次和重启均保留。查询在 SDK 返回后再次检查该状态，以覆盖等待期间发生的撤回。沿用原有状态、范围、到期与来源屏蔽校验，不放宽有效记忆的判定。

验收：先验证新增测试在旧实现上失败，再验证修复后通过；覆盖删除成功后提取失败、重开库后继续降级、重试成功恢复 SDK 查询、超过 20 条来源的分页重建、删除后无剩余来源，以及异步查询期间发生撤回。执行 `pnpm check`，并回退本次实现单独确认新增测试会失败。独立核实使用固定临时快照，不提交或覆盖工作树中已有的并行改动。

### P2 修复：撤回范围与到期边界

目标与范围：修复 review 剩余两项 P2，仅调整 Memory Store/Service 的撤回屏蔽和到期判定，补充测试；保留 P1 的重建降级、原有证据归属、来源撤回、版本与范围校验。

实现方案：

- 内容哈希与主题匹配均先核对撤回适用范围：全局撤回仍覆盖各目标，某目标内的撤回只屏蔽该目标；共享来源的撤回继续沿来源关系传播。同原文但来源独立的其他目标或全局记忆，应正常重建并绑定新 SDK 节点。
- 冲突比较只考虑尚未到期的同范围 active/conflict 记录，恰好到期也视为失效。过期历史不触发新冲突、不阻止新事实生效；查询不因已过期的冲突要求澄清。更正/冲突引用仍须校验所有者、范围、状态与来源先后；合法引用过期历史不能导致新事实被整条拒绝，也不把过期 conflict 自动升级为 active。

验收：两项问题各有旧实现失败的独立测试；覆盖其他目标/全局的独立同文记忆重建、同范围哈希屏蔽与全局撤回继续有效、到期瞬间无引用/更正引用/冲突引用的新事实、过期冲突的查询与后续写入，以及未过期冲突仍受保护。运行记忆测试与 `pnpm check`；在隔离副本分别回退两处修复确认对应测试变红，再由独立只读代理在固定快照核实。未实测部分不记为通过。

### 接入接口

宿主使用 Python 3.12 环境，固定安装 `hy-memory==2.0.16`。0600 env 文件需要 `MEMORY_LLM_API_KEY/BASE_URL/MODEL` 和 `MEMORY_EMBEDDER_API_KEY/BASE_URL/MODEL` 六项；其他 SDK 参数沿用 [阶段 0 实测配置说明](004-phase0-validation.md#33-hy-memory-接入中实际遇到的问题)。当前 MiniMax 配置用 `max_completion_tokens`、4096 输出预算、`reasoning_effort=low`、省略 temperature、`MEMORY_LLM_MAX_RETRIES=1`；百炼向量为 1024 维、batch size 10。不能把 SDK 的 retries=0 理解成“仍调用一次”。脚本启动时验证版本、权限与必填键，初始化失败只报告不可用，不回显配置。

构建后通过 `dsh-superagent/along-memory` 导出（Python 脚本随包分发）：

```ts
const memory = createAlongMemory(alongStore, {
  python: '/absolute/venv/bin/python',
  script: '/absolute/package/scripts/along-memory-service.py',
  dataDir: '/Users/<user>/.along/memory',
  envFile: '/Users/<user>/.along/memory.env', // 0600；不传密钥值
  workerRoot: '/absolute/dsh-state/work',
})
await memory.runBatch(boundUserId) // 一批最多 20 条，processed>0 时可继续调用
const result = await memory.search({ userId: boundUserId, goalId: boundGoalId }, query)
const context = memory.context({ userId: boundUserId, goalId: boundGoalId }, messagesFromDatabase)
memory.forget({ userId: boundUserId, goalId: boundGoalId }, memoryId)
// 关库之前先 await memory.close()。
```

`memoryTools(memory, scopeFor)` 提供两件 strict 工具，scopeFor 由宿主从 WorkLink 派工身份生成。Runtime 已加入 Worker allow-list、使用 `context()` 处理聊天规划历史，并提供当轮明确忘记的工具。`context()` 返回当前 `memories` 与带状态的 `history`；查询也分别返回这两类信息。当前不会自动启动批次；统一调度属于阶段 E。`search().needsClarification` 表示库中仍有冲突，模型先结合当前明确意图和带状态的上下文理解，无法判断时才追问；`degraded` 表示 SQLite 降级，缺失信息由对话侧询问。

## 3. 验收标准（先固定后执行）

1. 明确中文偏好成为 active；今天调整、当前目标约束、否定、引用、假设、助手建议、健康事件不能成为 active（BC-04-01/02/04/05/13）。
2. 通用偏好跨目标可读；目标范围内容不流入其他目标；缺失/外用户证据及更正关系拒绝，同范围明确更正唯一生效，未明确解决的冲突双方均 conflict（BC-04-03/06/07）。
3. 撤回之后立即查询、上下文装配、关闭重开库、同批次重跑、旧消息重新提取及 SDK 旧节点/摘要返回都不可使其生效；历史和已排任务保持一致（BC-04-08/09/10/14）。
4. SDK 故障查询返回 SQLite 有效记忆且标注 degraded；提取失败可重试、逻辑操作唯一、每次尝试可追踪；模拟 SDK 成功而 SQLite 提交前失败，重试不重复 active 版本（BC-04-12、§2.5.4）。
5. 删除失败留待清理，重试成功清除 SDK 投影；重建不处理被撤回证据，其他用户数据不删（BC-04-11）。
6. Python 协议用合成依赖做离线测试；已安装的真实 SDK + 中文合成对话做质量/写入/检索/重开验证。记录延迟与内存，短时冒烟不代表长期常驻稳定性通过。
7. `pnpm check` 通过；阶段 A 或其他并行改动导致的失败分别记录，不顺手改写其实现。

### 4.4 P1：删除完成与投影可用分别持久化

根因：`finishCleanup()` 在 SDK 删除成功时立即移除清理标记，查询据此误判 SDK 已恢复可用；此时重建失败或尚未跑完所有分页，未撤回的 SQLite 有效记忆会被空或不完整的 SDK 命中集合排除。删除完成不能作为投影可用的证据。

现已在现有 `meta` 中保存 `memory_rebuild:<userId>`，与删除清理项、重置进度原子提交。完成所有待处理操作与可提取来源之前持续降级；最后一批提交或无来源时完成重建。新撤回保留自己的清理代次，查询在异步返回后再次检查投影状态。记忆有效性与撤回校验的契约未变。

### 4.5 P2：按撤回范围屏蔽，按到期边界判定当前冲突

两项根因与修复：

- `suppressed()` 原来只给主题匹配加范围条件，内容哈希命中会绕过范围。现统一先判断撤回范围，再匹配哈希或主题。某目标中的撤回不再妨碍其他目标/全局的独立同文记忆重建；全局撤回、同范围哈希屏蔽及来源撤回传播保持有效。
- `apply()` 原来把所有 active/conflict 历史都参与当前冲突比较，`search()` 也未排除过期 conflict。现将未过期的当前比较集合与完整的关系引用校验集合分开，恰好到期即退出当前冲突判定；合法引用过期历史仍可通过已有校验，未过期冲突仍须明确解决。不会自动把旧 conflict 改成 active。

## 5. Runtime 接线方案（2026-11-16，按用户反馈修订）

目标：把现有独立记忆模块接入实际 Along 本地 Runtime，使 Worker 能召回并理解持续更新的长期记忆，结合当前聊天规划，关闭时不留下 Python owner 或数据库访问。不是阶段 E 调度，也不把本轮接线视为完整 D 质量验收。

范围与实现：

- 本地 Along 部署始终装配一个 `MemoryService`，共用 `along.sqlite`。新增可选的宿主配置 `alongMemory`（Python 可执行文件、SDK 数据目录、0600 env 文件的绝对路径）；Python 脚本由包内路径解析。未配置 SDK 时使用明确不可用的 backend，检索降级到 SQLite，仍支持即时撤回与上下文过滤；GitHub 部署不装配或读取这些配置。凭证值不进入 Worker 配置、提示词或日志。
- `Runtime.along.memory` 拥有模块；Along Worker 工具使用 WorkLink 动态绑定的用户与目标范围注册查询/撤回，加入 allow-list，沿用严格 schema 和 Harness lossless JSON 输出。聊天语义由 Worker 理解，不增加关键词规则或确认流程。
- `along_conversation_read` 保留原始对话的时间与顺序，并提供当前有效记忆及带状态的旧版本/候选/冲突/停用上下文。当前明确要求优先；新信息通常比旧信息更能说明当前偏好，但不是机械按时间覆盖所有事实，由模型结合语义理解与更正。旧版本不能伪装成当前有效事实，但无需完全对模型隐藏。
- 按用户反馈，不引入整段历史截止、通用 DSH 历史封锁或模型请求序列重置。明确“忘记”仍停用对应记忆，并过滤直接被撤回的来源；其他旧聊天继续可读。现有无完整派生来源图的摘要不能承诺精确脱敏，本轮不追求清除模型所有已读上下文。原始手机历史展示与 sync 不改变。
- 停机先停止投递和执行，等待记忆 owner/batch 关闭，再关业务库并释放锁。批处理入口保留给 E，当前不偷偷增加即时提取、定时器或休眠调度。

验收：真实 Runtime 工具注册与动态范围、跨用户/跨目标拒绝、SDK 未配置或故障的 SQLite 降级、查询与撤回输出 lossless JSON、当前指令/新旧版本的状态与顺序可读、明确忘记仅停用对应记忆和直接来源而保留其他聊天、历史与已有任务保留、重启后仍生效、停机先关闭记忆再关闭库、GitHub profile 不受影响。运行针对性测试和完整 `pnpm check`；真实 SDK/模型冒烟只使用合成中文数据，未执行的真机/长期质量验收保留为待验。

### 5.2 真实链路中的参数反馈

真实合成验证已走通记忆召回、长期偏好更正以及新版本优先。临时安排场景中，模型把 `task.update.base_revision` 传成字符串，严格校验正确拒绝；但工具层普通 union 的报错混入所有无关操作分支，模型连续重试没有修正。目标不是接受错误类型，而是让错误定位实际操作字段。

方案：工具参数按 `op` 区分操作，`goal.create` 内再按 `domain` 区分 custom 与数值目标。保留原来的严格字段、数值类型、custom metric 和完整业务校验。验收：重放字符串版本号和对象形状 context，错误分别直接落在 `ops[0].base_revision`、`ops[0].fields.context`；旧的创建目标边界继续通过，全量检查与真实合成场景复测分别登记。
