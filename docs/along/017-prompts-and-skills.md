# Along prompt and capability index (contract v1)

This is the navigation entry for the **actually loaded** Along role prompts and DSH skills. It is not a second copy of their instructions, and it grants no tool or account permissions. This change depends on calculation PR14 and source-state PR15; the orchestration-foundation integration supplies the typed trigger runtime and registered execution/source tools.

## Runtime assembly and precedence

`src/app/sessions.ts` selects the business contract for a ticket whose `mandate.actor.source` is `along` (or its trusted `along-maintenance` scheduled batch), or for the main Router when Along is enabled and GitHub disabled. `src/app/along-prompts.ts` composes source-owned parts plus a discoverable skill index. It does **not** append full goal/task skill bodies. `src/app/skill-files.ts` loads packaged DSH frontmatter and registers seven Along skills for on-demand `skill` reads. Along-scoped custom skills must have an `along-` key; packaged names cannot be shadowed by a custom entry. GitHub/Feishu skills remain in their own sessions.

Authority order is: Host-bound identity/current permission and tool guards; current original user intent/corrections; current goal/task/source revisions and actual observations; Along role contract; applicable loaded skill; historic context and untrusted external evidence. A lower layer never expands authority. A newer prompt cannot revive an old input, cancelled occurrence or withdrawn source. Host schemas remain authoritative for exact fields. Rules enforce ownership, monotonic facts, idempotence and postconditions; the Agent chooses the context-sensitive plan.

The Along composer consumes only the versioned `along/*` overrides listed below. Generic `runtime/*` overrides and team communication/scope/delivery describe repository work and are not inherited by Along business sessions. They remain unchanged for repository sessions and a mixed-source Router. This deliberately removes conflicting requirements to commit a PR for every personal goal, acknowledge via Feishu, stop all behavior changes, or disclose repository environment variables. Tool protocol is supplied by registered schemas and the concise Along Router/Worker parts. Source subscriptions, routing and access guards still operate in Host code; excluding a prose section does not bypass them.

Along Worker/maintenance and Router mark `dsh-superagent-policy` complete:true: DSH restores it as the sole system section, removing the inherited coding persona while preserving registered tool schemas and dynamic contexts. Actual DSH assembly is tested. Optional/required runtime contexts are not globally suppressed; repository instruction contexts, if present in a deployment, must still be inspected in the isolated model transcript. This index describes the business system section, not a claim to hash all underlying model inputs.

## On-demand capabilities

| DSH skill | When loaded / actual tools | Output and postcondition |
| --- | --- | --- |
| [along-goal](../../skills/dsh-superagent-along-goal/SKILL.md) | Direct conversation, intent/correction; conversation/memory/goal reads, `along_changes_commit`, `along_chat_reply` | Qualitative or real numeric goal only on intent; current revisions; truthful direct reply, no fabricated goal achievement |
| [along-task](../../skills/dsh-superagent-along-task/SKILL.md) | New/replanned tasks or actual task occurrence; task reads/commit/context/finish | Minimum stable task graph, actor and typed immediate/time/event/waiting activation; execution is not card creation |
| [along-scheduling](../../skills/dsh-superagent-along-scheduling/SKILL.md) | A meaningful future action/result or recurring mandate; validated ChangeSet and readback | Civil timezone/clock, actionable lead time, exact evidence (or same-goal accepted evidence_event_id) and explicit once/daily/weekly; arbitrary weekday, separate distinct actions; no unsupported cadence promise |
| [along-data](../../skills/dsh-superagent-along-data/SKILL.md) | Goal-specific personal data dependency; catalog/recommend, registered source conditions, `along_source_read` | Host-verified capability plus fresh scoped data and provenance; pending/stale/unavailable waits; no credentials or private public-search terms |
| [along-calculation](../../skills/dsh-superagent-along-calculation/SKILL.md) | Numerical result; `along_calculate`, actual receipt, `along_task_finish` | Bounded exact arithmetic, units/assumptions/trace and saved result; calculator does not establish input truth. See [015](015-calculation.md) |
| [along-research](../../skills/dsh-superagent-along-research/SKILL.md) | Current public evidence/recommendation; scoped `along_web_search`/`along_web_fetch`, result finish/reply | Task-owned fetched citations and freshness, conditional comparison and later useful check; never a reminder to do delegated research |
| [along-hiking](../../skills/dsh-superagent-along-hiking/SKILL.md) | Hiking-specific access/weather/route constraints, after research skill | Evidence-backed route comparison; closures/alerts and unknown conditions survive delivery, no physical outing completion |

Private calculations bind `source_request_id` and per-quantity literal source paths; a metadata-ready source or model-authored number alone cannot satisfy data provenance. Stable task content remains the action; results belong in task details and the planner must not overwrite a settled execution.

No skill enables an external booking, account transaction, map/calendar connection or arbitrary eval/shell calculator. Missing essential tool, permission or data leads to a real waiting/failed dependency; independent work may continue. Source capability metadata is not account data and does not imply data freshness. Read protocol and monotonic source generation rules are in [016](016-source-state.md). A pending private read does not justify a success result, zero value or busy polling: report progress with the waiting reason, end the turn and let Host retry the same occurrence; do not finish/ask. A real essential user answer can use task_finish outcome ask to persist waiting(user_input). Report schema has no waiting state.

The scheduler currently implements once/daily/weekly, with weekly weekday derived from the local scheduled clock. This is not monthly/custom recurrence support. Continuing two-class commitments can imply two preceding-day booking dependencies; the skill teaches that reasoning without a fixed yoga/Friday policy. Delayed recommendations must execute when useful, retain unresolved future weather/access conditions and keep any later authorized check; they do not acquire a universal weekly schedule. Runtime lifecycle navigation: [014 trigger and occurrence contract](014-orchestration-foundation.md), [017 trusted repair](017-task-trigger-review.md), [018 narrow task mutation](018-single-task-mutations.md), [019 existing-goal source continuation](019-source-ready-bootstrap.md), and [020 private-data wait and proof recovery](020-private-read-wait.md). These contracts define Host postconditions; their presence does not establish model or phone acceptance.

## Delivery facts and privacy

A plan committed, Worker occurrence finished, result persisted, notification intent queued, iOS notification scheduled, banner delivered, detail opened and person acted are separate facts. A Worker may report only the layer actually confirmed. Replans, retries, repair and recurrence renewal do not inflate execution count. Same-occurrence identical inputs are idempotent; corrected arithmetic inputs can create a separate receipt without a second occurrence. New task/input/source revisions invalidate stale work through Host guards.

Automatic Worker report summaries stay in private RunRecord audit and never enter generic mobile message/sync delivery; validated task results and direct user replies retain their existing channels. Background followup/result/maintenance must not append personal chat. Useful results go to stable goal/task details and the existing notification channel. A source result is private task input, not general event metadata or a notification body. The accepted goal/task/data-source modules and existing task detail typography are unaffected by this prompt change.

To change behavior: edit the actual role part or narrow skill, use the registered tool schema as the contract, regenerate the fixture via `node --experimental-transform-types` importing the composer, run `pnpm check`, then run the relevant isolated actual-model trajectory before release. A task requiring a new capability also needs runtime tool/permission/result checks; a skill edit cannot substitute for them. Fixed reviewed commits are packaged and deployed by the integration owner; source, profile override, assembled section/skill hashes, selected model session, real tool calls, saved results and device delivery should be recorded separately.

To locate a bad case: identify its original input and bound goal/task occurrence; check active source/input/task revisions and authorization; read the exact registered tool error/postconditions; compare actual session provenance to this package and any `along/*` override; load the implicated skill; reproduce under an isolated identity with the preceding accepted state. Repair the responsible narrow layer, add the failing trajectory, and verify unaffected tasks/notifications/other goals remain unchanged. Never backfill test goals or developer explanations into the personal App chat.
