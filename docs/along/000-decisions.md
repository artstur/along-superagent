# Along 决策记录

> 只记已定决策，每条写明决策、原因和影响。推翻某条时追加新条目，并在旧条目下注明被哪条替代，不改写旧条目。
>
> 架构见 [系统架构](001-architecture.md)，记忆与技能见 [记忆与技能](002-memory-and-skills.md)，阶段与验收见 [实施与验收](003-implementation.md)。

## D1 本地单用户优先

- **决策**：服务端由自己的 Mac 提供，首期按单用户、一个本地部署设计。
- **原因**：先在自己的 Mac 和 iPhone 上验证「有记忆、能跟进、少打扰」，再决定是否面向外部用户。
- **影响**：不建设公网接入、注册、计费和多租户运维；业务对象仍保留 `user_id` 归属检查。

## D2 基于 DSH Super Agent 构建 Along Agent

- **决策**：在 Along Agent 工程中扩展 DSH Super Agent，复用事件评估、授权、派工、执行与恢复机制。
- **影响**：扩展优先落在 Source、业务服务、工具和运行装配层，必要时才改核心模型。
- **命名（2026-11-16）**：Agent 工程统一称为 **Along Agent**，本地目录 `along-superagent`、包名及插件 ID `dsh-superagent`、远端地址保持不变。命名整理的范围、方案及验收见 Along 的 `docs/agent-architecture.md`。

## D3 全链路自动化：目标与任务校验后自动生效

- **决策**：Agent 总结、创建、修改、归档目标，新增、调整、取消任务；程序校验通过即生效。链路上不设采用、确认、审批或人工审核环节。用户不认可时通过聊天纠正。
- **原因**：用户 2026-11-15 明确要求全链路自动化。
- **影响**：
  - Along `AGENTS.md` 红线已改为「校验后自动生效」。现有 App 的「采用」流程是待迁移的旧行为。
  - 程序校验只用来拒绝坏数据和过时写入，不是等待环节。
  - 询问只用于缺少会改变判断的事实，不用于确认修改。

## D4 目标只能通过聊天改变

- **决策**：界面不提供直接编辑或删除目标的入口。用户想改目标，就在聊天里说。
- **原因**：用户 2026-11-15 决定；与 D3 一致，目标的所有变化都来自 Agent 的 ChangeSet。
- **影响**：客户端不再上报 `goal.updated`、`goal.archived`，也就不用区分「用户改的」和「Agent 改的」两种目标变更来源。任务完成反馈仍由客户端上报，它是事实，不是对目标的编辑。

## D5 健康数据首期沿用现有 7 类

- **决策**：首期只用当前 `HealthKitReader` 已读取的 7 类：步数、健身记录、活动消耗、体重、静息心率、睡眠期间手腕温度、睡眠，口径不变。
- **原因**：用户 2026-11-15 决定先按现有范围，后续再扩展。
- **影响**：替代 v0.4 的「HealthKit 全量类型接入」。事件协议为新增类型留位，加类型时不改协议。

## D6 第一期接入 Hy-Memory

- **决策**：第一期用 Hy-Memory（`pro`、`scene=chat`）做长期记忆的提取与召回；SQLite 保存记忆的治理状态。
- **原因**：用户 2026-11-15 决定。
- **影响**：增加一个仅本机访问的 Python 进程；Mac 安装兼容性在阶段 0 验证。Hy-Memory 故障时降级读取 SQLite 中的有效记忆，不默默补成事实。

## D7 复盘、记忆提取和 Skill 整理定时批量做

- **决策**：Worker 结束时只由宿主登记执行记录，不调用模型。复盘、记忆提取和 Skill 整理由定时作业批量处理。
- **原因**：每次 Worker 结束都调模型成本高，单次执行也不足以证明一个方法有效。用户 2026-11-15 同意。
- **影响**：当前目标的约束靠目标与任务本身和近期对话承载，不依赖记忆提取，因此批量延迟不会让刚说的话失效。用户删除记忆立即生效。

## D8 Worker 可以使用 DSH 已接入的能力

- **决策**：Along Worker 保留 DSH 给 Executor Session 的工作工具，以及 DSH 已接入的 Skill 和外部能力，再加上 Along 业务工具；不限制为只用 Along 工具。
- **原因**：用户 2026-11-15 决定。目标相关工作常需要查资料、计算或使用其他已接入服务。
- **影响**：边界不再靠缩小工具集，改为三条：业务状态只认 Along 工具的提交；凭证不进入 Worker 环境；有外部副作用的操作沿用 DSH Mandate 与 Policy。阶段 0 核实前两条。

## D9 一条健康事件影响多个目标时，逐目标独立提交

- **决策**：按目标拆成派生事件，各目标独立评估、独立提交 ChangeSet。某个目标冲突或失败只重试这个目标，不回滚其他已提交的目标。
- **原因**：用户 2026-11-15 确认；跨目标事务会让一个目标的冲突拖住所有目标。
- **影响**：目标之间需要共同考虑的约束（例如同一晚的总时长），由 Worker 把其他目标的当前任务作为上下文读取，不做跨目标原子提交。

## D10 Skill 自动发布，无人工审核

- **决策**：批量复盘产生的 Skill 经程序校验后自动发布启用；发布后效果变差时自动停用并回到上一版本。
- **影响**：发布条件与回退信号见 [记忆与技能 §3](002-memory-and-skills.md#3-技能)。

## D11 明确行动意图才自动建目标

- **决策**：用户明确表达行动意图时自动建立目标；仅描述现象时先回应，缺少意图才询问。
- **原因**：用户 2026-11-15 确认。描述现象不等于要求系统建立一个目标。
- **影响**：「我想改善睡眠」可自动建目标；「最近睡得不好」先回应，不能直接建目标。意图明确后仍按 D3 校验并自动生效，不增加确认环节。

## D12 普通变化只展示，按需要通知

- **决策**：普通变化只在目标里展示；需要用户回答、近期安排有实质变化或执行受阻时才通知。
- **原因**：用户 2026-11-15 确认。
- **影响**：Agent 运行完成或 ChangeSet 生效本身不构成通知理由；同步与通知分别处理。通知受 iOS 权限与执行机会限制，不承诺手机离线时即时送达。

## D13 忘记记忆不删除历史聊天

- **决策**：「忘记这件事」撤回对应记忆，不删除历史聊天。
- **原因**：用户 2026-11-15 确认。
- **影响**：治理状态立即撤回，派生记忆与索引按既定流程清理；历史聊天仍可查看。上下文装配与批量提取必须尊重撤回记录，不能把保留的旧聊天当作依据继续使用该记忆或重新激活它。

## D14 多目标冲突由 Agent 协调

- **决策**：优先遵守用户通过聊天明确的优先级和硬约束，其余由 Agent 自动协调；无法同时满足硬约束时才询问。
- **原因**：用户 2026-11-15 确认，不要求每次调整都由用户取舍。
- **影响**：扩展 D9 的跨目标上下文读取与独立提交规则，不增加人工采用环节；验收要检查协调结果遵守明确优先级和硬约束。

## D15 首期不做健康授权撤回流程

- **决策**：首期仅本人使用，不实现额外的健康授权撤回及关联历史数据清理流程。
- **原因**：用户 2026-11-15 明确不考虑该需求。
- **影响**：移出首期实现与验收范围。健康数据不可用、未同步与实际为零仍需区分；不绕过系统权限，不改变配对身份检查或 D8 的执行授权边界。此决定不涉及 D13 的记忆撤回。

## D16 忘记偏好不自动重排现有任务

- **决策**：忘记偏好后，后续规划不再使用该偏好；不因此自动取消目标或重排现有任务，历史聊天保留。
- **原因**：用户 2026-11-15 确认。
- **影响**：补充 D13。既有安排仍是业务状态，不能反向作为恢复已忘记偏好的证据；用户明确要求修改相关安排时，再按聊天提交新的 ChangeSet。

## D17 不设应用侧累计模型用量上限

- **决策**：不设置每日预算或累计模型用量上限，不因应用自设预算暂停后台规划、记忆提取或复盘。
- **原因**：用户 2026-11-15 明确无需限额。
- **影响**：批量处理仍按 D7 执行；模型调用量可记录和验证，但不作为预算熔断条件。本条不改变请求超时、失败重试和供应商实际额度等运行约束。

## D18 记忆更新保留上下文，当前意图优先

- **决策**：长期记忆会持续更新，正常更正保留新旧表达、时间/来源顺序及状态，让模型理解变化。当前明确要求优先；较新信息通常更能说明当前偏好，但不机械覆盖所有旧事实。不能因出现更新或一次忘记就截断其他历史或重置整个模型上下文。
- **原因**：用户明确要求让模型结合语义判断，以记忆的更新和使用为重点，避免把撤回治理做成信息屏障。
- **影响**：补充 D6、D13、D16。查询分别提供有效记忆与带状态的历史证据；旧版本、候选、冲突和已停用记忆不冒充当前事实。明确忘记仍立即停用对应记忆，直接来源不进入规划历史，但不清除无关对话，也不承诺抹除模型已读内容。冲突只有在当前意图和上下文仍无法判断时才询问。Runtime 接线不加入全局历史封锁或请求序列重置。

## D19 云端单机 2 用户部署（扩展 D1）

- **决策**：允许把 host 与 agent 链路部署到一台云服务器（Docker Compose），服务 2 个由服务端静态用户表声明的用户；每用户一次性配对码发码即授权，码走私下渠道。不建设注册、计费、审批和多租户运维。
- **原因**：用户于 2026-11-20 确定两人共用一台服务器。D1 的公网限制继续适用于 Mac 本地部署。云端允许预先声明的两位用户经公网 443 配对和访问，两种部署均保留业务对象的 `user_id` 归属检查。
- **影响**：Mac 本地与云端共用同一套源码，无模式开关，Mac 本地模式完整保留为回退路径；云端 v1 新链路数据面维持事件摄取开关的 503 语义，目标聊天链路照常全量过校验后自动生效；配对绑定按用户分条存储，服务端只存 token 哈希；公网配对码的防枚举用全局失败滑动窗口限速。设计与上线 Runbook 见 Along 仓库 `docs/cloud-deploy-multi-user.md`。
