name: dsh-superagent-along-task
description: Create and adjust Along user tasks after goal intent is established; handle constraints, chat feedback and changes to an existing plan.
---

Read the goal and existing tasks before planning. A user task is an action for the person; a DSH Ticket or Assignment is agent execution and never belongs in that list.

For a new goal, submit a small useful next step together with `goal.create`. For an existing goal, use stable task ids and revisions to update or cancel rather than copying tasks. Carry temporary constraints in goal context with an expiry when known. Preserve explicit priorities and hard constraints. Ask one specific question only when missing information changes the next step.

Submit related operations as one validated `along_changes_commit`. Do not request adoption. Completion feedback is a fact; it is not permission to change the goal. A correction supersedes the older plan: re-read the current conversation and task state before retrying.

For every new task decide its reminder in the same commit, including tasks suggested by you. Read the user timezone and current time from along_conversation_read. A deadline, session and reminder can be three different instants.

- An executable time-bound action with a usable window gets a future ISO scheduled_at with an offset and reminder_plan {state:"scheduled",source:"agent",explanation:"…"}. Choose a reasonable local time to make the action possible. Describe the reason and any lead time. The host puts your arrangement in the conversation. When the user specified the reminder clock itself use source:"user" and include exact evidence quoting that instruction. A deadline or a class time alone does not specify a reminder clock.
- “周二和周五上课，前一天要预约” → schedule the next Monday/Thursday booking action first, at a sensible time on the preceding day. Explain your choice. One task per distinct booking action if needed. If a release window materially determines when booking is possible and is genuinely unknown, use {state:"needs_time",question:"…"} naming the missing window. The host sends that question to chat; do not duplicate it via along_chat_reply. Do not require a user to configure each clock.
- “每天凌晨2点前入睡” gives a sleep deadline. Choose an earlier actionable winding-down time as an Agent arrangement for the next occurrence. Only mark a recurring reminder when there is a task-specific continuing mandate. Never call the chosen lead time user-specified. Ordinary untimed ideas use {state:"off",reason:"untimed"}; a declined reminder uses reason:"opt_out".
- repeat:"once" (default) does not renew. For an explicitly ongoing schedule set repeat:"daily" or "weekly", reminder_plan.evidence to the exact user clause authorizing that action and reminder_plan.action to its distinctive action text present in both that clause and task.content. Weekly uses the local reminder weekday, not the class day: “每周一上午提醒我预约周二的课程” binds Monday. Separate different weekly actions. A request at the end of a list to arrange its tasks and reminders applies to the listed recurring actions. For “我想每周二和周五上陶艺课，前一天要预约。每天凌晨2点前要收拾完画具。请帮我安排任务和提醒，具体提醒时刻你来安排”, create two distinct weekly booking tasks (e.g. “预约周二陶艺课” / “预约周五陶艺课”); cite the exact course/preceding-day phrase as evidence and “陶艺课” as the shared action, with reminders on Monday and Thursday. For the daily action, keep “收拾完画具” in both the quoted daily clause and task content and schedule an earlier useful time as source:"agent". Without a defensible ongoing mandate arrange the next occurrence once.
- Adjust the same task ID with its latest revision. task.update.fields.reminder_plan:"keep" preserves a previously verified plan when rewording the same action. When the time changes submit a complete replacement plan and future scheduled_at. Turn off a reminder without cancelling the task by setting reminder_plan:{state:"off",reason:"opt_out"}. Complete/cancel through existing task operations. Never start or renew reminders that the user declined.

For a requested recommendation now ready in an active goal, deliver it with along_chat_reply and notify:"recommendation_ready". For an actionable result use notify:"task_result". Include task_id only when verified. Routine planning and clarification do not produce extra alert notifications. A host-bound due review reads current state, then completes with along_health_followup. Already-bound daily/weekly mandates renew on ordinary keep. Never introduce recurrence from a due tick.


When current external facts or recommendations are necessary, read dsh-superagent-along-research; for hiking also read dsh-superagent-along-hiking. Use the Along web tools to obtain scoped citations. An existing task to research a destination executes that research when due through along_health_followup with its structured recommendation. Do not replace it with a generic reminder to research.

For a user chat that requires personal data, inspect `along_data_sources_catalog` before assigning manual export as the only route. Persist relevant source recommendations with `along_data_sources_recommend` in the current goal; catalog setup-only entries must be described as setup-only, never as a connected account or working OAuth. Current OKX capability opens official settings only; account sync, credential entry and App CSV upload/import are unavailable. Do not assign an immediate upload/import task, tell the user to upload CSV in the App, or promise to process files the App cannot receive. Manual CSV export is only a future integration alternative. Do not ask for API keys/secrets in chat or expose local Worker paths to an iPhone user. Automatic due/health work cannot invent user authorization or change source recommendations through a non-chat mandate.

Strict JSON and recovery:
- All revisions/input_version are JSON integers (`2`), never strings (`"2"`). Root base_revision is the goal revision; each task.update base_revision is that task's revision. Read both freshly. Keep scheduled_at/repeat in task.update.fields. reminder_plan accepts state/source/explanation/evidence/action only for a scheduled plan; never put scheduled_at/timezone/repeat in it. source is exactly agent or user, and explanation is always required.
- A recommendation in an existing goal needs no ChangeSet unless the user also authorized a task change. Deliver the result separately even if a requested reminder edit is unresolved; never spend the browsing budget trying to fix a reminder schema. An existing reminder can use keep when no clock/cadence changes are authorized. To add an authorized weekly cadence, set fields.repeat:"weekly" explicitly with a complete scheduled plan and the original task ID. Prose saying “每周” cannot replace that field. Verify the resulting task snapshot actually says weekly before telling the user it is weekly.
- invalid_arguments means no tool body ran. Correct the listed paths while preserving the COMPLETE envelope. Do not retry unchanged types, move nested fields to the root, or clear unrelated tasks. A business-invalid reason is a different failure: reread its guidance and original user evidence. A schema example grants no authority and its IDs/dates must never be submitted as actual user values.

If the actual original clock is unchanged, reuse it as the next valid authorized occurrence rather than inventing another time. If weekly cannot be validated, do not claim that a once plan met the weekly request. Explain the unresolved part normally while still delivering available research.

For an explicit “补上每周…” instruction, keep the complete exact command including “补上” in reminder_plan.evidence, with the distinctive shared action. Do not trim it to a bare “每周…” activity statement. When it specifies when to perform an action without saying “提醒/通知/叫我”, do not pretend it is source:user reminder-clock wording. Preserve the existing valid action time as source:agent with an honest explanation and the exact weekly action mandate. If that explicit weekly request remains unresolved, say so; do not silently replace it with once just to pass validation.

For a current explicit request to add a weekly cadence to the original bound task, verify the LIVE task snapshot before reporting ready: it must be open with the requested weekly day, zone and civil clock and a future next occurrence. Ordinary recommendation work does not require a reminder edit. Use the currently registered Along tools for an actual commit; a temporary package, isolated script test or a subagent's diagnostic report is not a live applied change. A truthful partial recommendation can be delivered separately, but does not complete the explicitly requested task update. On requested_weekly_plan_incomplete read the actual state, correct the same task via along_changes_commit and read it back; preserve the original valid next occurrence. If unable, report blocked/failed accurately instead of ready.

When both a task change and a recommendation are requested, prefer applying and reading back the necessary task change before sending its recommendation notification: notifications bind the current task revision. Sending a recommendation first remains legal, but a later task revision can make that earlier notification stale; a historical card is not proof that its notice still applies.

## Conversation boundary

Only a real inbound user chat may be answered with along_chat_reply. Scheduled/health work, reminder repairs, retries and developer acceptance are background operations, never user-authored dialogue. Finish automatic work through along_health_followup; the host delivers useful recommendations in task results and the existing notification channel without adding a chat utterance. An automatic ask remains background-only without push. Keep existing assessment report semantics: a settled need_data assessment is not completion of the real task. Do not force human action for routine missing observations; use existing blocked/Attention only for a real blocker. Existing task needs_time questions stay on the task card. Direct user conversations may clarify essential missing facts. Do not post execution summaries or development instructions to a personal conversation. Development and acceptance run against isolated identities/data, never by sending paired production user_message events. Message audience is host-owned and cannot be selected by a Worker.

along_conversation_read separates direct messages from task_feedback facts. A task_event is an observed task event, not a new person-authored conversation or permission to change a goal. Read current task and reminder state through the existing structured tools. Internal execution and development records are not user preferences.
