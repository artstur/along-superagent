---
name: dsh-superagent-along-task
description: Decompose a real goal into minimal user actions and Agent operations, bind activation/dependencies, execute occurrences and preserve unrelated state.
---

Read the original conversation, current goal, tasks and relevant authorized facts. Identify the desired outcome, current constraints, who acts, essential dependencies, and what would count as completion. Propose the smallest useful plan for this goal; no fixed task count or domain workflow. Preserve each unaffected task's content, status, schedule, reminder, recurrence and trigger. Update/cancel the same stable task ID and current revision only when justified; do not recreate it to escape a rejected edit.

Every newly created/replanned task has a typed `trigger`, not merely prose:
- `actor:user, capability:reminder` is an action for the person. A delivered reminder is not completion.
- `actor:agent, capability:research|calculation|reminder` is a genuinely supported operation. Execute it with tools when activated; creating an open card does not do the work. External bookings, payments, transactions, calendar writes or unsupported integrations must not be relabeled as one of these capabilities.
- `kind:immediate` means useful executable work now. No artificial future clock or recurring repeat.
- `kind:time` uses persisted scheduled_at/reminder_plan and the supported once/daily/weekly clock. Load the scheduling skill; a date in content alone is not a schedule.
- `kind:event` requires registered, goal-owned conditions. Current supported conditions are source_ready/source_updated for okx trading_account_summary, same-goal task_completed, or supported health_available. Use repeat once or on_change according to the actual mandate. Do not invent provider/capability/event strings, cross-goal dependencies or cycles. A source's ready capability does not imply its cached data is fresh.
- `kind:waiting` states the real reason and resume:user_input|capability_available. Use for missing essential input/authorization/tool; do not call an external action done. Independent useful work can still execute. Time/immediate tasks may include registered conditions; unmet conditions gate execution without inventing facts.

Read the live schemas for exact supported fields. Persist source recommendations before subscribing dependent tasks. A newly created prerequisite needs its real Host-issued task ID before a later task can depend on it; do not guess IDs or create circular placeholders. Changing the goal's task graph is not permission to alter unrelated tasks. Unsupported recurrence/conditions must be explicit waiting/partial work, not a silent once substitute.

Submit related operations with `along_changes_commit`. Integers remain integers; root base_revision is the goal revision and task.update base_revision is that task's revision. Changed fields belong under task.update.fields. Use trigger:"keep" or reminder_plan:"keep" only when the live semantics and clock/cadence are unchanged and the tool permits it. Read back actual trigger, task, reminder and recurrence after a requested change. A business-invalid or invalid_arguments response means the requested change did not apply: repair the specified fields in the complete envelope, do not repeatedly submit the same invalid payload or claim success.

For a dispatched operation call `along_task_context` first. It supplies the actual task/actor/capability, occurrence and current goal/task/input revisions. Load only the matching execution skill. Use `along_calculate` for bounded arithmetic and retain its persisted receipt; use scoped Along search/fetch for public evidence; use `along_source_read` for authorized private data. Pending/stale/unavailable source reads are durable waiting work: end the attempt honestly for Host resumption, without polling or finishing successfully. Failed attempts and replanning do not count as executions.

Finish the occurrence through `along_task_finish` with outcome keep when no ChangeSet was applied, update only after actual applied changes, or ask for an essential unresolved fact when its schema permits. Calculation requires its actual calculation_receipt; research requires the complete structured recommendation. The Host validates result scope and persists task details/notification intents. Keep standing daily/weekly tasks open: finishing this run does not end the series. One-off Agent task completion is subject to Host postconditions. Physical activity, booking or sleep completion requires actual user feedback or appropriate authorized evidence.

Automatic health assessment instead finishes through `along_health_followup` with the actually relevant types. No background execution, repair, retry, development or acceptance message belongs in `along_chat_reply`. Direct user conversations alone may reply there. Task results and existing notification intents are distinct from system delivery, opening the task, and the person's action. Never infer those later facts or issue duplicate progress alerts.

For pending/stale/unavailable private reads, do not call along_task_finish or use outcome ask: record orchestrator_report state:progress with the concrete waiting reason and end the turn for Host retry of this occurrence. There is no report state named waiting. A genuinely essential missing user answer can instead use the supported task_finish outcome ask to persist waiting(user_input); that is not an automatic success.
