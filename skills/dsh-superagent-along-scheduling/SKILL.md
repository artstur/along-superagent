description: Choose and persist useful civil times, lead time and authorized once/daily/weekly cadence; handle deadlines, separate weekdays, corrections and recurring occurrence review.
---

Read the original intent, current time/timezone from `along_conversation_read`, current tasks, reminder plans and stored cadence. Distinguish the activity deadline, execution window, prerequisite release time, reminder time and result delivery window. Choose a reasonable actionable time from this goal and facts; never apply a universal clock. User permission to arrange reminders lets you choose a time, but does not make your choice a user-specified clock.

For `trigger.kind:time`, persist a future ISO scheduled_at with an explicit offset and a complete reminder_plan:{state:"scheduled",source:"agent"|"user",explanation:"…",evidence?,action?}. The Host retains civil timezone/clock and next occurrence; do not place timezone/repeat/scheduled_at inside reminder_plan. Use source:user only for exact original reminder-clock wording; source:agent for a reasoned arrangement or lead time. No field or prose may promise a timezone different from the bound user's actual timezone. If unknown essential timezone/window changes the action, ask/needs_time rather than silently assume it.

Supported calendar cadence is repeat:once|daily|weekly. Omission is once, not recurrence. Recurring commitments require exact task-specific original user evidence in reminder_plan.evidence and a distinctive reminder_plan.action present in that evidence and task content. Set repeat explicitly when requested; a text mentioning “每周” is not persistence. The weekly weekday is derived from the actual local scheduled_at, so any weekday is valid, not a fixed Friday. A cadence with multiple distinct weekly actions needs separate stable tasks/plans. Unsupported monthly/custom interval rules must remain honestly unresolved rather than misrepresented as daily/weekly.

Understand a continuing goal in context: if the person commits to Tuesday and Friday classes and booking the preceding day, both recurring booking actions are implied dependencies of those recurring classes, even if “每周” is not repeated before every list item. Arrange both preceding weekdays with task-specific evidence and a useful booking time. Preserve later opt-outs/one-off limitations. This is an example of dependency reasoning, not a yoga-specific rule. If a booking release window is essential and unknown, use reminder_plan:{state:"needs_time",question:"…"} or a typed waiting task and continue independent steps. Never pretend a reminder itself reserves the class.

For a daily before-02:00 deadline, evaluate the next actual local overnight occurrence relative to now. Choose an earlier useful lead time; do not blindly attach today's 02:00 after it has passed, or offset by 24 elapsed hours across timezone transitions. Generic bedtime is not a medical policy. For research, persist the delegated research execution time when evidence can be useful and separately preserve any authorized later check; do not notify far ahead with an expired forecast or substitute “go research” for actual Agent research. Read the research skill for evidence expiry and conditional delivery.

An untimed user action may explicitly use reminder_plan:{state:"off",reason:"untimed"}; a declined reminder uses reason:opt_out. Missing meaningful clock uses needs_time with the actual missing question. Do not invent an arbitrary immediate trigger to hide an unresolved user action schedule. Never renew declined, cancelled, completed or explicitly one-off actions. Preserve existing valid plans with keep only when unchanged; a clock/cadence change needs complete replacement plan and current revision. Turning notifications off does not itself cancel the task; cancellation uses the task operation and invalidates old occurrences.

After commit read the live task/reminder/trigger: verify requested repeat, local weekday, civil clock, timezone, future next occurrence and both dependent weekly actions where requested. If the Host rejects evidence or an unsupported cadence, correct the same tasks or explain the limitation; a once plan cannot satisfy requested recurrence. Existing due/restart logic renews valid stored series and recovers missed windows; a due tick does not authorize a new cadence or guess that a stale reminder was delivered. Keep recurring Agent research/calculation tasks open and finish only the current occurrence. Retries/reviews/renewals are not new executions or user actions.


When repairing a plan from an already accepted original direct conversation, the registered scheduled reminder_plan may include evidence_event_id naming that exact same-goal original user event plus exact evidence/action. Read its original message and later corrections first. This is a Host-validated evidence reference, not permission to quote another goal, revive revoked authority or fabricate a new chat. Preserve accepted original intent; do not post repair/renewal explanations as personal chat. A later explicit stop or one-off restriction overrides the older recurring mandate. A genuine weekly user task.completed records that occurrence and retains the next authorized weekly action; cancel only on an actual stop, not merely because this week's action finished.
